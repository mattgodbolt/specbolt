# The 6502, as a test of the format

A spike, 2026-09-27, on branch `mg/v4_spike_6502`: the documented NMOS 6502 described in refract's `.cpu` format,
compiled into a disassembler and an interpreter beside the Z80, to find out whether the format is expressive for a
second, quite different CPU. The question was not whether every opcode runs cycle-exactly but whether the description
captures the chip's regularities or degenerates into a listing of opcodes, and where it bends.

Part of [v4's notes](../NOTES.md), and the answer to its "What a second CPU would need".

---

## Result

*The description on the branch now uses `mode` blocks; see [Modes, tried](#modes-tried). The figures here are the
baseline they were measured against.*

**The whole documented instruction set is described without changing refract**, in 46 rows plus a catch-all for the
151 documented opcodes: 0.30 rows per opcode. It compiles, and smoke tests disassemble a spread of opcodes and run a
counted loop with a branch, a subroutine call and return, and both indirect addressing modes, in the same test binary
as the Z80, whose tests still pass. The files are `z80/v4/m6502/` (machine, palette, target, `6502.cpu`) and
`z80/v4/test/M6502Test.cpp`, kept under v4 only so the spike reuses its build and test wiring.

Where the rows go:

| rows | opcodes | what | why that many |
|---:|---:|---|---|
| 8 | 63 | the accumulator group (`ora` … `sbc`, `sta` included) | one per addressing mode |
| 5 | 28 | read-modify-write (`asl` `rol` `lsr` `ror` `dec` `inc`) | one per addressing mode |
| 11 | 22 | loads, stores and compares of X and Y | one per addressing mode; X and Y share each |
| 1 | 8 | branches | none: one row |
| 1 | 7 | the status instructions | none: one row, a hole for `tya` |
| 3 | 6 | `tax`/`tay`, `inx`/`iny`, `php`/`pha` | each pair shares a row on one bit |
| 17 | 17 | one opcode each | irregular in the hardware |

**Every row that claims a single opcode is irregular in the chip itself**: `bit` (two modes), `jmp` and `jmp (ind)`,
`tya`, `txa`, `txs`, `tsx`, `dey`, `dex`, `nop`, `plp`, `pla`, `brk`, `jsr`, `rti` and `rts`. None of them shares an
encoding pattern with a sibling whose behaviour it shares, so no format could fold them without a table of exceptions.
The first draft had seven more, one `sta` per mode; those went into the accumulator rows (see *What worked* below).

**What the ratio would be with the one change that matters**: about 31 rows, 0.21 per opcode, if an addressing mode
could be a vocabulary member (see the first blocker). The 24 per-mode rows would become about nine: one per group for
the memory modes, and immediate and accumulator kept apart because they are not addresses.

## Modes, tried

2026-09-28. The first blocker below, an addressing mode that cannot be a vocabulary member, prototyped as a `mode`
block and the whole description rewritten with it.

**Result: 28 rows plus the catch-all, for the same 151 opcodes, down from 46**, beside 27 lines of mode members and
four modes derived in a line each. Every group is one row: the accumulator group, `sta`, read-modify-write,
`ldx`, `ldy`, `stx`, `sty`, the compares, `bit` and `jmp`. What remains one row per opcode is the irregular remainder
the baseline already listed. The Z80 is untouched and still passes, including zexdoc.

The grammar, as implemented:

```
mode-decl   = "mode" , name , [ "=" , mode-name , "with" , renaming , { "," , renaming } ] ;
renaming    = value , "->" , ( "-" | mode-name , "." , value ) ;
member      = value , { "n" } , "|" , text , "|" , operand , "|" , [ steps ] ;
value       = bit , { bit } ;                  (* the slice's value, most significant bit first *)
```

A `mode` line opens a block, as `table` does: the lines after it, up to the next declaration, are its members, and a
value with no line is a hole. A row names a mode with the reference syntax it already had, `{am:b}`. In the mnemonic
it renders the member's text; in a step it stands for the member's operand; and the member's steps run before the
row's own, once, however many times the row names it.

```
mode am
000 n   | ($nn,x) | (ea) | zp_index ea <- n x ; zp_pointer ea <- ea
010 n   | #$nn    | n    |
100 n   | ($nn),y | (ea) | zp_pointer ea <- n ; index ea <- ea y
111 n n | $nnnn,x | (ea) | index ea <- n x
...
mode store = am with 010 -> -

aaabbb01 | {alu:a} {am:b}     | {alu:a} a, p <- a {am:b} p
100bbb01 | sta {store:b}      | ld8 {store:b} <- a
aaabbb10 | {rmw_op:a} {rmw:b} | {rmw_op:a} {rmw:b}, p <- {rmw:b} p
01j01100 | jmp {jm:j}         | ld16 pc <- {jm:j}
```

**What worked**

- **The disassembler needed nothing.** A member's text is lowered to pieces like any member's, and rendering a
  vocabulary piece already renders the member's pieces, so `$nn` inside a mode renders and consumes its bytes.
- **Bodies already split by mode.** A row's reference to a mode reads its slice, so `body_key` gives each mode its own
  body, and the number of immediate bytes becomes a property of the body rather than the row (`immediate_bytes_of` in
  Execute.hpp). The members' steps are put in front of the row's (`steps_of_body`), and nothing else in the generator
  changed.
- **A mode named twice runs once.** `inc $nnnn,x` names `{rmw:b}` as operand and destination; its address is formed
  once and the write-back delay still applies, because both resolve to the same address. Seven cycles, as the chip.
- **One mode serves loads, stores and read-modify-writes.** The machine owes the page-crossing fix-up when `index`
  forms an address, and the access that follows settles it: a read pays only if it crossed, a write always pays. That
  is what the chip does, a dummy read at the unfixed address, and it removed the baseline's `into`, `from` and
  `indexed` vocabularies and `index_store`. Checked: `lda $nnnn,x` four or five cycles, `sta` five, `inc` seven.
- **Holes and derivation cover the irregular columns.** `sta` has no immediate (`store = am with 010 -> -`); `stx`,
  `sty` and the compares are `ldx` and `ldy` with holes; `bit` and `jmp` are one-bit modes.
- **Exhaustive visits found every place a new kind of member needed a decision**, at compile time: resolving an
  operand, a view's members, liveness, the location list, what an operation is, and the conditions check.

**Design considerations and strains**

1. **A derived mode can only borrow what another mode has.** `ldx` indexes by `y` where `ldy` indexes by `x`, and the
   zero-page `$nn,y` exists in no other mode, so `ldx` is written out in full rather than derived. The right-hand side
   implemented is `-` or `mode.value`; an inline member (`101 -> n | $nn,y | (ea) | zp_index ea <- n y`) would put
   `|` and `;` inside a comma-separated list, which reads badly and parses worse. Recommendation: keep `mode.value`,
   and accept writing a mode out when it has no donor.
2. **A row must name a mode in its mnemonic exactly where it names it in its steps.** The disassembler finds a mode's
   bytes through its text and the interpreter through its steps, and the two must agree about length, so this is
   checked (`check_modes_named`). A mode used only for its steps, or only for its text, cannot be written.
3. **Precedence reads backwards for the groups.** The read-modify-write row claims the slots where `dex` and `nop`
   sit (as `dec a` and `inc a`), and an earlier row may overlap a later one only by being inside it, so the
   single-opcode rows must come first and the groups after. Natural for a decoder, odd for a reader who expects the
   general case first.
4. **An instruction still has one immediate.** A row naming a mode that fetches may not fetch its own (checked). The
   6502 never needs both; a CPU whose addressing mode and instruction each carry bytes would need the rule relaxed and
   an order stated (the member's bytes first, following the Z80's displacement).
5. **Two kinds of vocabulary.** A `mode`'s members are pieces of a row and a `vocab`'s are operands or operations; a
   mode's member used where an operation belongs is refused, and a view may not select from a mode. Neither came up,
   but both are rules a reader has to learn.
6. **A member's steps cannot name references.** They are written against the member's own bytes and no opcode, so
   there is no slice for `{v:s}` to read. Nothing in the 6502 wanted it.
7. **The `.cpu` aligner** now treats `mode` as the start of a run, as it does `table`, so each block aligns on its own.
8. **Capacities.** A member runs at most a few steps and a row names at most two modes (`Fragment::max_steps`,
   `max_modes_named`), both limits of the spike rather than of the design.

**What the framework change touched**: Model.hpp (`Member::Fragment`, `Vocabulary::mode`, `Step` moved ahead of
`Member`), Lexical.hpp (`is_mode`), Parse.hpp (mode blocks in `parse_vocabularies`, `parse_fragment`,
`rename_members`, the immediate checks split into helpers, `check_modes_named`, and `parse_rows` skipping member
lines), Execute.hpp (`fragments_of`, `immediate_bytes_of`, `steps_of_body`, and `execute_one` using them), a
`Fragment` case in each visit over a member's kind, and a non-`const` `Vector::data()`, without which a `Vector` is
not a contiguous range. The Z80's `(ix+d)` was not moved onto modes; it may be a mode in waiting, but its displacement
arriving before the opcode (`dd cb d op`) is the part a mode does not model.

## The shape of `6502.cpu`

```
vocab alu     = ora:ora8 and:and8 eor:eor8 adc:adc8 sta:sta8 lda:lda8 cmp:cmp8 sbc:sbc8
vocab into    = a    a    a    a    (ea) a    a    a
vocab from    = (ea) (ea) (ea) (ea) a    (ea) (ea) (ea)
vocab indexed = r:index r:index r:index r:index w:index_store r:index r:index r:index
vocab xy      = y x
vocab other   = x y
vocab cond    = bpl:bit_clear(0x80) bmi:bit_set(0x80) bvc:bit_clear(0x40) bvs:bit_set(0x40) \
                bcc:bit_clear(0x01) bcs:bit_set(0x01) bne:bit_clear(0x02) beq:bit_set(0x02)

aaa00001 n   | {alu:a} ($nn,x)  | zp_index ea <- n x ; zp_pointer ea <- ea ; {alu:a} {into:a}, p <- a {from:a} p
aaa10001 n   | {alu:a} ($nn),y  | zp_pointer ea <- n ; {indexed:a} ea <- ea y ; {alu:a} {into:a}, p <- a {from:a} p
aaa11101 n n | {alu:a} $nnnn,x  | {indexed:a} ea <- n x ; {alu:a} {into:a}, p <- a {from:a} p
101101r0 n   | ld{xy:r} $nn,{other:r} | zp_index ea <- n {other:r} ; load8 {xy:r}, p <- (ea) p
fff10000 n   | {cond:f} $e      | {cond:f} p ; branch pc <- pc n
00100000 n n | jsr $nnnn        | delay 1 ; dec16 ea <- pc ; push16 ea ; ld16 pc <- n
01100000     | rts              | delay 2 ; pull16 ea <- ; inc16 pc <- ea ; delay 1
```

## What worked unchanged

- **Operations as vocabularies over `aaa`.** One row serves a whole group, exactly as `{arith:q}` does for the Z80,
  and holes free the cells the irregular instructions occupy: `stx` and `ldx` sit in the read-modify-write column,
  `tya` in the status column, and each is a hole there and a row elsewhere.
- **Several vocabularies over one slice**, which is how the chip's decode works: `alu`, `into`, `from` and `indexed`
  all read `aaa`, so `sta`, which writes where the rest of its group reads and always pays for a page crossing, is one
  member of each rather than seven rows of its own. The same trick makes `ldx $nn,y` and `ldy $nn,x` one row: `xy`
  names the register and `other` the one it is indexed by, both over one bit.
- **Branches on status bits** are one row: the condition is a vocabulary of `Continue`-returning operations, each
  member binding the bit it tests, and the relative target renders as the address it lands on.
- **Indexed and indirect addressing, as steps.** An indexed or indirect mode forms its address in `ea`, a location the
  machine declares for the chip's internal address latch, and the access is then through `(ea)`: `(zp),y` is
  `zp_pointer ea <- n ; index ea <- ea y`, then `(ea)`. NOTES.md predicted that nested indirection and indexing by a
  register would block; they do not, because a step can name any location, and one standing for the address latch is
  honest about what the chip does.
- **Data-dependent cost.** A page crossing costs a cycle on a read and always on a write: `index` charges only when
  the page changes, `index_store` always, and the row (or the `indexed` vocabulary) says which. A taken branch charges
  through `branch`. NOTES.md predicted `displaced_address` would need telling read from write; it is not used at all,
  and nothing needed to change.
- **Read-modify-write**, dummy write included, is `(ea)/delay=1` as a destination read through the same address: the
  Z80's write-back delay, unchanged.
- **The stack, calls and returns**: machine operations for page one (`push8`, `pull16` and so on), and `jsr`/`rts`
  adjusting the return address in steps.

## Blockers and bends, by how much of the instruction set they cost

1. **An addressing mode cannot be a vocabulary member.** *Costs about fifteen rows, the whole remaining excess.* The 6502 puts
   its mode in `bbb`, which is what a vocabulary is for, but the members differ in what they fetch (`#` and `zp` one
   byte, `abs` two) and in what they do before the access (`($nn,x)` two steps, `$nn` none). A member is an operand
   and nothing more, and the encoding's bytes belong to the row, so every group has one row per mode and each mode's
   address-forming steps are written out again in every group that uses it. What the description wants to say:

   ```
   mode am = ($nn,x): n  | zp_index ea <- n x ; zp_pointer ea <- ea
             $nn:     n  | ld16 ea <- n
             $nnnn:   nn | ld16 ea <- n
             ...
   aaabbb01 | {alu:a} {am:b} | {am:b} ; {alu:a} {into:a}, p <- a {from:a} p
   ```

   **The change:** a vocabulary whose members are *fragments* of a row, each with its own encoding bytes, its own
   rendered text and its own steps, spliced into the row that names it. Immediates would become a property of the
   decoded opcode rather than of the row (the `(ix+d)` displacement machinery already derives a fetch per opcode, so
   there is precedent), `check_immediates` would count per opcode, and the disassembler already renders a member's
   pieces. This is the one change that would take the description from 0.30 to about 0.21 rows per opcode, and it is
   what NOTES.md's first blocker predicted; its second and third blockers are subsumed by it, because a fragment can
   hold the steps that form an indexed or indirect address.
2. **A member cannot render an immediate.** Part of the first: a member's text may not contain `$nn`, so even a
   same-width mode vocabulary could not render its operand. Goes with 1.
3. **Immediates render as `0x..`.** The disassembler's number format is the framework's, so `lda #$42` renders as
   `lda #0x42`. A target should be able to supply the format; small.
4. **An encoding byte the action ignores cannot be declared.** `brk` is two bytes, the second ignored, but the column
   agreement check insists the action uses every `n`. It is written as one byte with the machine skipping the next,
   so the disassembler gives it length 1. An encoding letter for a skipped byte would fix it; small.
5. **A palette's helpers become operations.** Every public static function of a palette is a verb, so the helpers the
   6502's operations share (`nz`, `with`) are nameable from a row. Harmless, and a `private:` section would hide them.

## Not attempted

Decimal mode, the undocumented opcodes (the catch-all spends a cycle and does nothing), interrupts and reset, and cycle
counts beyond what the steps charge, none of which was checked against the chip. None of these is a question about
the format.
